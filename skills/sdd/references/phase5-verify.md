# Phase 5 — 验证与交付(整体验收)

## 目标

从「代码写完了」走到「可以交付了」。验收的对象不是代码,是**规范**——
逐条回放 acceptance criteria,确认每一条都被真正实现。

## 输入

- `specs/<feature>/proposal.md`(全部 AC 是验收清单)
- `specs/<feature>/design.md`(接口契约、架构约束、非功能指标)
- `specs/<feature>/tasks.md`(全部 Task 已勾选)
- 实际代码与测试

## 输出

`specs/<feature>/acceptance-report.md`,版本推进到 `v1.0`。

## 四个验收维度

| 维度 | 怎么验 |
|---|---|
| **功能** | 逐条回放 AC:AC → 覆盖它的 Task → 对应测试用例 → 实际跑 → 记录结果 |
| **接口** | `design.md` 的接口签名逐条与实际实现比对:参数、返回值、错误语义、不变量 |
| **架构** | 模块边界是否被破坏(跨层依赖检查)、单一职责是否被稀释、ADR 里的决策是否被遵守 |
| **性能** | `proposal.md` §3.2 的每个量化指标 → 实测,给出实测数字与指标对比 |

### 功能:AC 回放矩阵

这是验收的核心表格,一行一条 AC:

| AC | 描述 | 覆盖 Task | 测试用例 | 结果 |
|---|---|---|---|---|
| AC-F-001 | 空表单提交返回 422 | TASK-003 | `test_empty_form.py::test_returns_422` | ✅ 通过 |
| AC-P-001 | P95 < 200ms | TASK-006 | 压测脚本 `bench.py` | ❌ 实测 P95 = 310ms |
| AC-E-001 | 并发扣款余额不为负 | TASK-005 | `test_concurrency.py::test_no_negative` | ✅ 通过 |

**任何一条 AC 未通过,整体结论就不能是「通过」。**

### 接口一致性

对 `design.md` §3 的每个接口签名逐条核对:
- 参数与语义一致?
- 返回值结构一致?
- 错误语义一致(design 承诺的错误码/异常类型)?
- 不变量被维护?

### 架构一致性

- 有没有模块依赖了它「不做什么」范围内的东西?(职责边界被突破)
- 有没有出现 design 里没有的新模块或新外部依赖?
- ADR 里的决策是否被遵守(例如选了 append-only 日志,实现里却做了原地修改)?
- 跨层依赖方向是否正确(上层可以依赖下层,反之不行)?

### 性能实测

对 `proposal.md` §3.2 的每条量化指标实测,给出:

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| P95 响应时间 | < 200ms | 310ms | ❌ 未达标 |
| 并发用户数 | ≥ 500 | 800 | ✅ 达标 |

**指标未达标是需求未完成,不是"基本达标"。** 结论写清楚。

## 结论

三档,由人拍板(AskUserQuestion):

- **通过** —— 全部 AC 通过,四维度无遗留问题 → 版本推进 `v1.0`
- **有条件通过** —— 明确列出遗留项与其风险(哪些 AC 未过、原因、是否阻塞上线)
- **不通过** —— 存在阻塞性问题,回到 Phase 4 修复(或走逆向修改流程调整规范)

AI 给出**建议结论 + 依据**,人决定最终结论。不要自己宣布通过。

## 收尾

1. 用 `assets/templates/acceptance-report.md` 生成报告
2. **跑行为自检**:`python <skill目录>/scripts/verify_acceptance.py --feature <feature>`
   —— 它会核对每条 AC 是否真的验过、结果是否与 tasks 的勾选状态一致、结论是否与实测相符。
   有错误就修报告或补验证,不要带着错提交。
3. **AskUserQuestion 确认后** git commit 验收报告:
   `docs(spec): 完成 <feature> 验收报告 v1.0`
4. 打 tag:`git tag -a v1.0 -m "<feature> 首版完成"`
5. 更新 `proposal.md` §0 版本号为 `v1.0`,在 changelog 记录
6. 若有未达标 AC:在 `tasks.md` 里新增补做 Task(或走逆向修改流程调整规范),不要留着不说

## 常见坑

| 坑 | 表现 | 修正 |
|---|---|---|
| 只跑一遍测试就说通过 | 没做 AC 回放 | 逐条 AC 对到测试用例 |
| 验收标准里没有的"显然没问题" | 漏测边界场景 | 以 AC 清单为准,不凭感觉 |
| 实测不达标但写成"基本达标" | 交付了不合格版本 | 未达标就是未达标,写进遗留项 |
| 只验功能不验架构 | 模块边界已破 | 四维度逐项过 |
| AI 自己宣布通过 | 无人拍板 | 结论由人确认 |
| 验收报告没进 git | 证据链断在最后一米 | 报告和代码一起提交,并打 tag |
