# 跨阶段约定

三份规范文档共享的编号、版本、ADR 与追溯规则。任何阶段开始前读这一份就够了。

## 编号规范

| 前缀 | 含义 | 出现在 |
|---|---|---|
| `AC-F-xxx` | 功能验收标准 | proposal §3.1 |
| `AC-P-xxx` | 性能验收标准 | proposal §3.2 |
| `AC-E-xxx` | 边界场景验收标准 | proposal §3.3 |
| `ASM-xxx` | 假设 / 开放问题 | proposal §5、design §5 |
| `ADR-xxx` | 架构决策记录 | design §2 |
| `TASK-xxx` | 任务 | tasks §1 |

编号在各自文档内**从 001 连续递增,不复用**。删除一条验收标准时不要重排后续编号,
保留空缺并在 changelog 说明——编号是追溯锚点,重排会让历史引用全部失效。

## 版本号

| 版本 | 含义 | 达成条件 |
|---|---|---|
| `v0.1` | 最小可行 | proposal.md 完成并通过 Gate |
| `v0.5` | 基线规范 | 三份文档齐备并通过校验 |
| `v1.0` | 首版完成 | 实现完成、全部验收通过 |
| `v1.x` | 增量 | 新增功能 / 修复,向后兼容 |
| `v2.0` | 不兼容变更 | 破坏性变更,需用户明确确认 |

版本号写在 `proposal.md` §0 与 `tasks.md` §0 两处,保持一致。

## ADR 规则

**只追加,不删除。**

ADR 结构:

```markdown
### ADR-003: 用 PostgreSQL 而非 MySQL

- **状态**:已采纳
- **背景**:需要事务与 JSONB;团队已有 PostgreSQL 运维经验
- **选项**:
  - A. PostgreSQL —— 支持 JSONB 与部分索引;代价:需新部署
  - B. MySQL —— 团队熟悉;代价:JSON 能力弱、部分索引缺失
- **决策**:选 A
- **理由**:JSONB 是本项目订单快照模型的关键;部署成本是一次性的,
  而 JSON 能力不足会长期拖慢迭代
```

状态取值:`提议` / `已采纳` / `已废弃` / `已被 ADR-xxx 取代`。

废弃一个决策时的写法:

```markdown
### ADR-002: 用 Redis 做会话存储
- **状态**:已被 ADR-007 取代
```

**原文保留**,只改状态行,并在新的 ADR 里写明取代原因。不要删除、不要改写历史条目——
历史决策记录了当时的约束和认知,删掉它就没人能解释代码为什么长这样。

## 追溯矩阵

规范的价值在于可追溯。链条是:

```
proposal AC  →  design 条目  →  Task  →  测试用例  →  实际结果
```

- **proposal → design**:design §6 的追溯矩阵,每条 AC 指向承接它的设计条目
- **design → tasks**:每个 Task 的「输入」引用 design 的接口或模块
- **tasks → 测试**:每个 Task 有验证命令
- **全链 → 结果**:phase5 的 AC 回放矩阵

链条上任何一环断了,就说明某个需求可能悄悄没被实现。`validate_specs.py` 会检查
proposal → design → tasks 这三段的闭合。

## 变更记录(changelog)

三份文档末尾都有变更记录章节,记录:

```
| 日期 | 版本 | 变更 | 原因 | 影响 |
|---|---|---|---|---|
| 2026-10-30 | v0.1 | 完成 proposal 初稿 | — | — |
| 2026-11-05 | v0.5 | ADR-003 引入 PostgreSQL | 需要 JSONB | TASK-002 改为用 PG |
```

**逆向修改**(阶段 3/4 发现缺陷后回头改规范)必须在这里留痕:改了什么、为什么、
影响哪些 Task/AC。没有留痕的逆向修改,事后无法区分「有意的演进」和「规范漂移」。

## 细粒度经验值

这些是经验值,不是硬规则,但超了通常意味着文档该拆了:

| 对象 | 建议上限 | 超出时 |
|---|---|---|
| proposal.md 行数 | ≤ 300 行 | 拆成多个 feature |
| 单个 proposal 的 AC 数 | ≤ 30 条 | 按子域拆分 |
| 单个 design 的模块数 | ≤ 12 个 | 考虑子系统边界 |
| 单批 Task 数 | ≤ 12 个 | 分 M1/M2 批次 |
| 单个 Task 涉及文件数 | ≤ 8 个 | 拆 Task |

## 反模式对照表

| vibe coding 症状 | SDD 修正 |
|---|---|
| "先做个 demo 看看" | 至少写清 §2.2 三条"不做什么" + 三条 AC,再写代码 |
| 一句话需求就直接开写 | 先过 Phase 1 的 Gate 清单 |
| "技术选型你定就行" | 仍然给 2–3 个选项 + 代价让人确认;默认也要确认 |
| 任务拆成"写完所有模块" | 拆到"一组文件 + 一条验证命令"的粒度 |
| 代码能跑就算过 | 跑 AC 回放矩阵,四维度验收 |
| 规范过期了没人管 | 逆向修改流程:改规范 → 用户确认 → 再改代码 |
| 规范和代码悄悄分叉 | 提交前跑 `validate_specs.py`;代码提交必须能追溯到 Task |
| 需求变更直接从代码改起 | 自上而下:proposal → design → tasks → 代码 |
| ADR 被就地改写 | 追加新 ADR,旧条目标「已被 ADR-xxx 取代」 |
| 用"实现细节"写验收标准 | AC 描述可观测行为,实现细节留给 tasks |
