# 跨阶段约定

三份规范文档共享的编号、版本、ADR 与追溯规则。任何阶段开始前读这一份就够了。

## 编号规范

| 前缀 | 含义 | 出现在 |
|---|---|---|
| `AC-F-xxx` | 功能验收标准 | proposal §3.1 |
| `AC-P-xxx` | 性能验收标准 | proposal §3.2 |
| `AC-E-xxx` | 边界场景验收标准 | proposal §3.3 |
| `ASM-xxx` | 假设(已先这么定,design 直接承接) | proposal §5、design §5 |
| `OQ-xxx` | 开放问题(还没定,需人拍板) | proposal §5、design §5 |
| `ADR-xxx` | 架构决策记录 | design §2 |
| `TASK-xxx` | 任务 | tasks §1 |

编号在各自文档内**递增,不复用**。删除一条验收标准时不要重排后续编号,
保留空缺并在 changelog 说明——编号是追溯锚点,重排会让历史引用全部失效。

`ADR-xxx` 在项目内拆了多个规范集时按**项目内全局连续**编号(见下方「ADR 编号」),
其余前缀始终在各自文档内递增。

## 版本号

| 版本 | 含义 | 达成条件 |
|---|---|---|
| `v0.1` | 最小可行 | proposal.md 完成并通过 Gate |
| `v0.5` | 基线规范 | 三份文档齐备并通过校验 |
| `v1.0` | 首版完成 | 实现完成、全部验收通过 |
| `v1.x` | 增量 | 新增功能 / 修复,向后兼容 |
| `v2.0` | 不兼容变更 | 破坏性变更,需用户明确确认 |

版本号写在**三份文档各自的 §0 元信息**表里,**三份始终保持一致**,代表该 feature
的当前版本。改了版本号要三份一起改,否则读者会看到 proposal 是 v1.0 而 design 还是 v0.5。

§0 元信息表在每份文档的开头,包含:项目(feature 名)、版本、状态、日期、关联文档。

## ADR 规则

**只追加,不删除。**

ADR 结构:

```markdown
### ADR-003: 用 PostgreSQL 而非 MySQL

- **状态**:已采纳
- **背景**:需要事务与 JSONB;团队已有 PostgreSQL 运维经验
- **选项**:
  - A. PostgreSQL —— 支持 JSONB 与部分索引;代价:需新部署
  - B. MySQL —— 团队熟悉;代价:JSON 能力弱、部分索引缺失
- **决策**:选 A
- **理由**:JSONB 是本项目订单快照模型的关键;部署成本是一次性的,
  而 JSON 能力不足会长期拖慢迭代
- **对应 AC**:AC-F-001
```

状态取值:`提议` / `已采纳` / `已废弃` / `已被 ADR-xxx 取代`。

废弃一个决策时的写法:

```markdown
### ADR-002: 用 Redis 做会话存储
- **状态**:已被 ADR-007 取代
```

**原文保留**,只改状态行,并在新的 ADR 里写明取代原因。不要删除、不要改写历史条目——
历史决策记录了当时的约束和认知,删掉它就没人能解释代码为什么长这样。

### ADR 编号

| 场景 | 规则 |
|---|---|
| 一个规范集覆盖整个项目(**默认**) | 编号在该规范集内从 001 连续 |
| 项目内拆了多个规范集 | 编号在**项目内全局连续**,不按规范集重启;跨文档引用写全限定名 `<feature>/ADR-002` |

两种场景都要求:**严格递增、无重复**。全局编号场景下,某个规范集的首个 ADR 可能是 003
(前面的号被别的规范集占了),这是正常的,不要求它从 001 开始。

**编号重启是规范层的多真相源。** `ADR-001` 在两个目录里指两件不同的事,只能靠人工
约定消歧 —— 正是这份规范要治的病。默认不要拆;拆了就要保证全局编号。

### ADR 与验收标准的分工

**一个行为只在一处定义,其余地方引用。**

| 位置 | 写什么 | 不写什么 |
|---|---|---|
| `proposal §3` | **行为契约的唯一事实源** | —— |
| `design §2` ADR | 只写**为什么**这样决定 | 不复述行为;要提行为时用「对应 AC」字段引用 |
| `design` 的证据小节 | 只标注「哪条有实测支撑」 | 不复述行为 |
| `proposal §6` 缺口清单 | 只记录**与契约的偏离** | 不复述契约 |

常见的坏味道是同一个行为在 proposal §3、design §2 ADR、design 的证据小节、
proposal §6 各写一遍 —— 结果一个行为改动要同步四处,必然漂移。

**ADR 解释为什么,行为定义在 proposal §3。** ADR 里必须提到某条行为时,填
`对应 AC: AC-F-012`,不要把行为抄一遍。

### 可覆盖值

常量若可被环境变量或配置覆盖,**不要写死字面值**:

- 差:`探针的最高重排分不低于 0.05` —— 设了环境变量后这条 AC 就与现实脱节,且无人发现
- 好:`探针的最高重排分不低于当前生效的相关度门限(默认 0.05,可用 `RAG_MIN_TOP_RELEVANCE_SCORE` 覆盖)`

判断方法:这个数字在生产环境里是**恒定的**还是**可配的**?可配的就必须写出覆盖方式。
proposal §3 的 AC 与 design §4 的非功能约束要写一致。

## Delta 变更语义

规范不是一次性写完的。每一轮修订都要说清**这一轮变了什么**,否则多 feature 并行时
没人说得清某个 AC 到底是新加的、改过的,还是一直都在。

在条目**行尾**加 delta 标记,使用 OpenSpec 的同名关键字:

```markdown
- **AC-F-003**: 给定...,系统 SHALL ... <!-- ADDED -->      本轮新增
- **AC-F-002**: 给定...,系统 SHALL ... <!-- MODIFIED -->   本轮修改
- **AC-F-001**: 给定...,系统 SHALL ... <!-- REMOVED -->    本轮移除
```

> 写文档里的**示例**时,编号用 `AC-F-NNN` 这种不匹配真实格式的占位——否则示例会被
> 校验器当成真的验收标准,报出「编号重复」和幻影 AC。

规则:

| 标记 | 含义 | 处理方式 |
|---|---|---|
| `ADDED` | 本轮新增的验收标准 | 必须同步补 design §6 追溯条目与 tasks §4 的 Task,否则校验报错 |
| `MODIFIED` | 本轮修改的验收标准 | 校验器会列出下游受影响的设计条目与 Task,提示复核 |
| `REMOVED` | 本轮移除的验收标准 | **原文保留**,只加标记;同时清理 design/tasks 中对它的引用 |

REMOVED 不删原文,理由与 ADR 一样——编号是追溯锚点,删掉会让历史引用失效。

`validate_specs.py` 会基于 delta 算出影响面:

```
[警告] specs/user-auth: AC-F-002 标记为 MODIFIED,下游需复核 → design §3.2 `auth.issueToken`; tasks TASK-003
[错误] specs/user-auth: §4 追溯矩阵未覆盖 AC-F-003(本轮标记为 ADDED,新增需求尚未拆成 Task)
```

`export_openspec.py` 会把带 delta 的 AC 导出成 OpenSpec 的
`## ADDED Requirements` / `## MODIFIED Requirements` / `## REMOVED Requirements` 三段结构。

## 假设与开放问题

proposal §5 分两类,编号前缀不同,下游处理方式也不同:

| 前缀 | 含义 | design 阶段怎么处理 |
|---|---|---|
| `ASM-xxx` | 假设——先这么定了,design 直接承接 | 在 design §5 写明"前提 + 不成立时的退化方案" |
| `OQ-xxx` | 开放问题——还没定,需要人拍板 | **必须先解决**,解决不了就写进退化方案 |

分开编号的意义在于:design 读到 `OQ-xxx` 时知道"这件事还没定,不能直接往下推",
读到 `ASM-xxx` 时知道"按这个前提设计,并写好退路"。

## 追溯矩阵

规范的价值在于可追溯。链条是:

```
proposal AC  →  design 条目  →  Task  →  测试用例  →  实际结果
```

- **proposal → design**:design §6 的追溯矩阵,每条 AC 指向承接它的设计条目
- **design → tasks**:每个 Task 的「输入」引用 design 的接口或模块
- **tasks → 测试**:每个 Task 有验证命令
- **全链 → 结果**:phase5 的 AC 回放矩阵

链条上任何一环断了,就说明某个需求可能悄悄没被实现。`validate_specs.py` 会检查
proposal → design → tasks 这三段的闭合。

## 变更记录(changelog)

三份文档末尾都有变更记录章节,记录:

```
| 日期 | 版本 | 变更 | 原因 | 影响 |
|---|---|---|---|---|
| 2026-10-30 | v0.1 | 完成 proposal 初稿 | — | — |
| 2026-11-05 | v0.5 | ADR-003 引入 PostgreSQL | 需要 JSONB | TASK-002 改为用 PG |
```

**逆向修改**(阶段 3/4 发现缺陷后回头改规范)必须在这里留痕:改了什么、为什么、
影响哪些 Task/AC。没有留痕的逆向修改,事后无法区分「有意的演进」和「规范漂移」。

## 细粒度经验值

这些是经验值,不是硬规则,但超了通常意味着文档该拆了:

| 对象 | 建议上限 | 超出时 |
|---|---|---|
| proposal.md 行数 | ≤ 300 行 | 拆成多个 feature |
| 单个 proposal 的 AC 数 | ≤ 30 条 | 按子域拆分 |
| 单个 design 的模块数 | ≤ 12 个 | 考虑子系统边界 |
| 单批 Task 数 | ≤ 12 个 | 分 M1/M2 批次 |
| 单个 Task 涉及文件数 | ≤ 8 个 | 拆 Task |

## 反模式对照表

| vibe coding 症状 | SDD 修正 |
|---|---|
| "先做个 demo 看看" | 至少写清 §2.2 三条"不做什么" + 三条 AC,再写代码 |
| 一句话需求就直接开写 | 先过 Phase 1 的 Gate 清单 |
| "技术选型你定就行" | 仍然给 2–3 个选项 + 代价让人确认;默认也要确认 |
| 任务拆成"写完所有模块" | 拆到"一组文件 + 一条验证命令"的粒度 |
| 代码能跑就算过 | 跑 AC 回放矩阵,四维度验收 |
| 规范过期了没人管 | 逆向修改流程:改规范 → 用户确认 → 再改代码 |
| 规范和代码悄悄分叉 | 提交前跑 `validate_specs.py`;代码提交必须能追溯到 Task |
| 需求变更直接从代码改起 | 自上而下:proposal → design → tasks → 代码 |
| ADR 被就地改写 | 追加新 ADR,旧条目标「已被 ADR-xxx 取代」 |
| 用"实现细节"写验收标准 | AC 描述可观测行为,实现细节留给 tasks |
