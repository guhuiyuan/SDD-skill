# Phase 4 — 代码生成(按 tasks.md 执行)

## 目标

把 tasks.md 变成代码。纪律只有一条:**验证不通过,绝不推进到下游**。

按规范写代码和 vibe coding 的区别不在于写得快慢,而在于**每一步都有客观的通过判据**。

## 输入

- `specs/<feature>/tasks.md`(必读:Task 定义、依赖、验证命令)
- `specs/<feature>/design.md`(实现时的接口依据)
- `specs/<feature>/proposal.md`(边界与 AC,防止实现跑偏)

## 输出

代码 + 更新后的 `tasks.md`(勾选与验证记录)+ 提交历史。

## 单个 Task 的闭环协议

每个 Task 严格走完这七步,一步都不跳:

1. **实际读取**该 Task 的定义 + 其依赖 Task 的产出文件。
   不凭记忆、不凭上一轮对话的印象——上下文会被压缩,文件不会。
2. **确认前置** Task 的验收已通过(`[x]` 且验证命令曾跑通)。
3. **实现**:在 Task 声明的文件范围内改。不做 tasks.md 之外的事,
   不顺手重构无关代码,不新增 proposal 里没有的功能。
4. **运行该 Task 的验证命令**。这是唯一的通过判据。
   > **命令跑不了怎么办**:被权限门拦下(auto 模式的安全分类器不可达)时,
   > **不推进 Task、不默认通过**。按 SKILL.md「受限环境下的降级与解锁路径」的
   > AskUserQuestion 三选项处理(切模式后重试 / 用户手动跑并贴回输出 /
   > 跳过并标记待人工校验)。被跳过的 Task 保持未勾选,Gate 结论标「未验证」。
5. **失败处理**:原地修复并重跑。**连续 2 次失败 → 停下升级给用户**,
   说明症状、已尝试的方案、以及你倾向的方向,让用户决定是否改设计。
6. **通过后**:把 `tasks.md` 对应 Task 改为 `[x]`,并记录实际验证结果
   (命令 + 关键输出,例如 `12 passed`)。
7. **AskUserQuestion 确认后** git commit。代码提交与规范提交同一标准,一律先问。

## 并行调度

同一批中互不依赖的 Task(标记 `[P]` 的组):

- 在**同一条消息里**发出多个子 agent,不要一条一条来
- 每个子 agent 必须拿到:Task 完整定义、依赖产出文件路径、验证命令、修改范围边界
- **prompt 里写明「验证命令原样执行」**,不要让子 agent 自己拼成 `cd X && …` 复合形式
- 子 agent 必须回传**验证命令的实际输出**,而不是「已完成」
- 有文件写冲突风险时(同批次涉及同一文件),不要并行,改为串行
- 主 agent 负责逐个核对子 agent 的验证输出,不能只看它说「通过」
- **子 agent 继承的是会话级设置,不是本技能的 `allowed-tools`** —— 技能的
  `allowed-tools` 只在通过 Skill 工具正式调用时对该技能调用的工具生效
  (changelog 1353),而且不覆盖子 agent。所以放行规则必须装进项目的
  `.claude/settings.json`(见 `install_hook.py`),否则子 agent 的每条命令
  都会撞权限门,**并行直接失效**
- **hook 也覆盖「派发」这一步**(第三组 matcher:`Agent|Task`)——
  放行的只是派发动作;子 agent 内部跑命令仍走同一份白名单(它继承会话级设置)。
  没有这一组,auto 模式下分类器不可达时,连派发都会被拒,这一节整个用不了

## 变更处理

### 新需求进来

自上而下,不许跳级:

```
改 proposal.md → 改 design.md → 改 tasks.md → 才动代码
```

每一步都要跑 `validate_specs.py`、都要 AskUserQuestion 确认、都要提交。
直接写代码等于把需求变更藏进了 commit 历史,规范从此失真。

### bug 暴露设计缺陷

逆流而上:

1. **停下当前 Task**
2. 说明缺陷:哪个 AC / 哪个接口 / 哪条 ADR 与实现现实冲突
3. 给出 ≥2 个修正方案 + 各自代价
4. AskUserQuestion 让用户选
5. 改 `design.md`(及受影响的 tasks 标记回 pending),在 changelog 留痕
6. 回到本 Task 继续

**不要静默地改代码来绕过规范。** 绕过一次,规范就失去约束力,后面所有验收都失去依据。

## 自检清单(每个 Task 结束时)

- [ ] 只改了 Task 声明范围内的文件
- [ ] 验证命令跑通,输出已记录
- [ ] `tasks.md` 已勾选并记录了验证结果
- [ ] 没有新增 proposal 之外的功能
- [ ] 新增的依赖/配置/密钥处理符合 design 的非功能约束(尤其安全与错误处理)
- [ ] 提交前已 AskUserQuestion 确认

## 常见坑

| 坑 | 表现 | 修正 |
|---|---|---|
| 凭记忆实现 | 没读依赖产出,接口对不上 | 每次都实际读文件 |
| 验证命令跑不起来 | 环境问题就跳过 | 环境问题也要报告,不能默认通过 |
| 顺手多做一点 | 超出 Task 范围 | 记到 tasks.md 的"后续"里,本期不做 |
| 一次改十个文件 | 无法定位失败 | 一个 Task 一组明确文件 |
| 并行写冲突 | 子 agent 互相覆盖 | 同文件不并行,或用 worktree 隔离 |
| 验收失败仍往下走 | 上游缺陷被下游掩盖 | 停在原地,修复或升级 |
| 规范与代码分叉 | 代码实现和 design 不一致 | 走逆向修改流程,不要绕 |
