# Phase 1 — 定义需求(proposal.md)

## 目标

把用户脑子里的一句话意图,变成一份**从未参与过的人(或 AI)也能准确复述**的需求规范。
完成的标志不是"文档写完了",而是"通过了下面的 Gate 清单"。

## 输入

- 用户的一段核心意图(可能只有一句话)
- 可能存在的现有代码库 / 旧文档(用于判断 brownfield 场景与既有约束)

## 输出

`specs/<feature>/proposal.md`,版本推进到 `v0.1`。

## AI 动作序列

### 1. 解析意图,列出已知与缺失

对照 `assets/templates/proposal.md` 的每个小节逐项判断:

| 模板小节 | 状态 | 谁来补 |
|---|---|---|
| §0 元信息 | 缺失 | AI 自动填(项目名、日期、feature 名) |
| §1.1 背景 | 缺失 | 问用户 |
| §1.2 目标 | 缺失 | 问用户(核心) |
| §1.3 目标用户 | 缺失 | 问用户(核心) |
| §2.1 做什么 | 部分缺失 | 问用户 |
| §2.2 不做什么 | 缺失 | **必须问,目标 ≥3 条** |
| §2.3 技术约束 | 缺失 | 可选,问一次 |
| §3.1 功能验收 | 缺失 | AI 起草,交用户确认 |
| §3.2 性能验收 | 缺失 | **必须问出具体数字** |
| §3.3 边界场景 | 缺失 | AI 起草,用户补充 |
| §4 术语表 | 按需 | 只收录不常见但重要的词 |
| §5 开放问题与假设 | 缺失 | AI 主动填写,编号 `ASM-001` |

### 2. 选项化提问

用 AskUserQuestion,每批 ≤4 问,按「对下游影响程度」排序。

**第一批(最高影响,必问)**
1. 目标用户 / 使用场景
2. 本期明确**不做什么**——给选项提示常见排除项:多租户 / 移动端 / 离线 / 复杂权限 / 报表 / 国际化 / 数据迁移
3. 性能与规模的硬指标——给选项:并发用户数、响应时间、数据量上限
4. 强制的技术约束——语言 / 框架 / 部署环境 / 必须用的中间件

**第二批(视第一批答案而定)**
- 与现有系统的集成点与依赖
- 已知的边界场景与历史 bug
- 合规、安全、审计要求

每个问题给 2–4 个**实质差异**的选项 + 每项一句说明 + 推荐项(首位标 "(推荐)"）。
提问前先给出基于上下文的推断默认值与依据,让用户做增量修正。

示例:

> 本期「不做什么」的范围到哪里?
> - **只做 Web 单端,不做移动端 (推荐)** —— 依据:当前仓库只有前端骨架,后端与移动端都要从零起
> - **Web + 移动端同时做** —— 工作量约翻倍,本期只能砍掉其他功能
> - **先做后端 API,前端下一期** —— 与当前仓库状态最匹配

### 3. 起草 proposal.md

复制 `assets/templates/proposal.md` 骨架逐节填写:

- 验收标准编号:`AC-F-001` 功能 / `AC-P-001` 性能 / `AC-E-001` 边界
- 每条 AC 写成「给定 X,当 Y 时,系统 SHALL Z(可观测结果)」
- AI 拿不准的地方写进 §5 并编号 `ASM-001`,**不要静默编造**
- §2.1 的目标只写结果,不写手段("用 Redis 缓存"属于 design)
- **修订已有规范时**(不是第一次写):给变动的 AC 加 delta 标记,
  `<!-- ADDED -->` / `<!-- MODIFIED -->` / `<!-- REMOVED -->`,写在条目行尾。
  这样下游影响面可计算,多 feature 并行时不会互相踩。详见 `conventions.md` 的 delta 章节。

### 4. 自检 Gate

对照下面的清单逐条核对。任何一条不通过,回到第 2 步补问,不要带着缺口往下走。

### 5. 展示草稿并确认

把草稿摘要(目标复述 + 做什么 / 不做什么 + AC 数量 + 假设清单)呈现给用户,
用 AskUserQuestion 确认:「按此定稿 / 需要调整 XX / 我要改范围」。

### 6. 固化

1. `python <skill目录>/scripts/init_specs.py <feature>`(若目录尚未创建)
2. 写入 `specs/<feature>/proposal.md`
3. `python <skill目录>/scripts/validate_specs.py --feature <feature>`
4. 更新 §0 版本号为 `v0.1`
5. **AskUserQuestion 确认后** git commit:`docs(spec): 完成 <feature> proposal v0.1`
6. `python <skill目录>/scripts/update_claude_md.py --feature <feature>` 把规范注入 CLAUDE.md

## Gate 检查清单

- [ ] **目标明确** —— 能写出「本项目要解决 X,让 Y 角色能 Z」,并让用户确认该复述准确
- [ ] **范围有界** —— §2.2 ≥ 3 条,且每条是「本期排除」而非「以后再说」
- [ ] **AC 可测试** —— 每条 AC 能转成一个自动测试用例:明确输入 + 可观测结果 + 二值判定
- [ ] **性能已量化** —— §3.2 每条含具体数字(P95 < 200ms / QPS ≥ 500 / 数据量 ≤ 100 万)
- [ ] **边界已覆盖** —— §3.3 至少覆盖:空输入、超长输入、并发、权限不足、依赖失败
- [ ] **术语一致** —— 术语表存在时正文只用表内词,无同义词混用
- [ ] **可被陌生 AI 理解** —— 不依赖对话上下文,不出现「如上所述」「那个接口」
- [ ] **细粒度适中** —— ≤300 行、≤30 条 AC;超出则提示拆成多个 feature

## 完成判据

`validate_specs.py` 对该 feature 的 proposal 部分 0 错误,且用户已确认定稿。

## 常见坑

| 坑 | 表现 | 修正 |
|---|---|---|
| 把"不做什么"写成"以后再说" | §2.2 变成愿望清单 | 每条都要能判断「本期是否真的没做」 |
| AC 不可测 | 「系统响应要快」 | 换成「P95 < 200ms,并发 500」 |
| 目标里塞了实现 | 「用 Redis 缓存用户信息」 | 目标写结果,手段留给 design |
| AI 默默替用户做决定 | 假设被当成事实写进 §2.1 | 所有假设进 §5 并编号,定稿时一并过目 |
| 术语表写了但正文没用 | 读者按正文理解 | 术语表只收录正文实际出现的词 |
| AC 数量爆炸 | 30 条 AC,细到实现细节 | AC 描述**行为**,实现细节留给 tasks |
| 一句话需求直接开写 | 跳过 Gate | Gate 未过不进 Phase 2 |
