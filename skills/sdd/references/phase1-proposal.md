# Phase 1 — 定义需求(proposal.md)

## 目标

把用户脑子里的一句话意图,变成一份**从未参与过的人(或 AI)也能准确复述**的需求规范。
完成的标志不是"文档写完了",而是"通过了下面的 Gate 清单"。

## 输入

- 用户的一段核心意图(可能只有一句话)
- 可能存在的现有代码库 / 旧文档(用于判断 brownfield 场景与既有约束)

## 输出

`specs/<feature>/proposal.md`,版本推进到 `v0.1`。

## AI 动作序列

### 0. 两个必须先答的决策

写任何内容之前先答这两个,答案不同,后面所有写法都不同。

#### 决策一:这份规范是什么模式?

读 `references/modes.md`,判定是 **build**(定义要做什么)还是 **as-is**(固化现在是什么)。

| 模式 | 判据 | §1.2 目标怎么写 | §3 的 AC 描述 |
|---|---|---|---|
| build | 要新建或改造功能 | 一层:系统要达到什么 | 系统**应该**达到的行为 |
| as-is | 系统已存在且在运行,要固化现状 | **两层**:系统要保证什么 + 规范要达成什么 | 系统**现在**必须保持的行为 |

判定结果要告诉用户,不要默认。

#### 决策二:覆盖整个项目,还是只覆盖一个 feature?

**默认结论:一个项目一套基线规范。** 模块边界画在 `design.md` §1.1 的模块划分表里
(那本来就是它的职责),不画成多个 feature 目录。

只有当下面四条**全部**成立时才拆成多个 feature:

| 判据 | 拆的信号 | 不拆的信号 |
|---|---|---|
| 事实是否跨模块边界 | 每条事实只在一个模块内 | 同一条事实被多个模块引用(如某个阈值既是 A 模块的探针阈值又是 B 模块的检索门限) |
| 单一权威值 | 各模块各有独立权威值 | 同一常量有多个候选真相源 |
| 评测 / 证据资产 | 各自独立 | 共享同一份评测集 |
| ADR 编号 | 能保持项目内全局唯一 | 拆开必然编号重启 |

**切分的代价是规范层出现多真相源。** 规范刚在代码层治好「同一事实散落在多处」,
切分后很可能在规范层复发:同一个数字被两个 feature 各钉一次,同一份评测集被
重新分类两遍,ADR 编号各自从 001 起导致 `ADR-001` 在两个目录里指两件事。

**拆了必须做两件事,否则别拆:**

1. ADR 编号在**项目内全局连续**,不按 feature 重启;跨文档引用写全限定名
   `<feature>/ADR-002`
2. 项目级事实(评测集分类、缺口清单、证据版本绑定规则)只在**一个** feature 里写,
   其余引用不复制

拿不准就问用户:「这份规范是覆盖整个 <项目名>,还是只覆盖其中一部分?」
—— 用选项把两种划法的后果摆出来(见下方提问示例)。

### 1. 解析意图,列出已知与缺失

对照 `assets/templates/proposal.md` 的每个小节逐项判断:

| 模板小节 | 状态 | 谁来补 |
|---|---|---|
| §0 元信息 | 缺失 | AI 自动填(项目名、日期、feature 名) |
| §1.1 背景 | 缺失 | 问用户 |
| §1.2 目标 | 缺失 | 问用户(核心)。**as-is 模式要问出系统层目标 + 规范层目标两层** |
| §1.3 目标用户 | 缺失 | 问用户(核心)。要问出「谁用这个系统」与「谁读这份规范」两栏 |
| §2.1 做什么 | 部分缺失 | 问用户 |
| §2.2 不做什么 | 缺失 | **必须问,目标 ≥3 条**。as-is 模式额外要求写明「不修改生产代码」 |
| §2.3 技术约束 | 缺失 | 可选,问一次 |
| §3.1 功能验收 | 缺失 | AI 起草,交用户确认 |
| §3.2 性能验收 | 缺失 | **必须问出具体数字** |
| §3.3 边界场景 | 缺失 | AI 起草,用户补充 |
| §4 术语表 | 按需 | 只收录不常见但重要的词 |
| §5 开放问题与假设 | 缺失 | AI 主动填写,编号 `ASM-001` |

### 2. 选项化提问

用 AskUserQuestion,每批 ≤4 问,按「对下游影响程度」排序。

**第一批(最高影响,必问)**
1. 目标用户 / 使用场景
2. 本期明确**不做什么**——给选项提示常见排除项:多租户 / 移动端 / 离线 / 复杂权限 / 报表 / 国际化 / 数据迁移
3. 性能与规模的硬指标——给选项:并发用户数、响应时间、数据量上限
4. 强制的技术约束——语言 / 框架 / 部署环境 / 必须用的中间件

**第二批(视第一批答案而定)**
- 与现有系统的集成点与依赖
- 已知的边界场景与历史 bug
- 合规、安全、审计要求

每个问题给 2–4 个**实质差异**的选项 + 每项一句说明 + 推荐项(首位标 "(推荐)"）。
提问前先给出基于上下文的推断默认值与依据,让用户做增量修正。

示例:

> 本期「不做什么」的范围到哪里?
> - **只做 Web 单端,不做移动端 (推荐)** —— 依据:当前仓库只有前端骨架,后端与移动端都要从零起
> - **Web + 移动端同时做** —— 工作量约翻倍,本期只能砍掉其他功能
> - **先做后端 API,前端下一期** —— 与当前仓库状态最匹配

覆盖范围的提问示例(决策二):

> 这份规范覆盖到哪里?
> - **整个 YuanRAG 项目,一套规范 (推荐)** —— 依据:相关度门限 0.05 同时被 agent 的探针
>   和检索层引用,`tests/eval/` 的 30 个评测用例也是全项目共享的。拆开会让同一个数字
>   在两份规范里各钉一次,ADR 编号也会各自从 001 重启
> - **只覆盖 agent 问答流水线** —— 检索、摄取与 HTTP 接口留到下一轮;代价:跨模块的事实
>   要等下一轮才能定论,本轮的 AC 可能得返工

### 3. 起草 proposal.md

复制 `assets/templates/proposal.md` 骨架逐节填写:

- 验收标准编号:`AC-F-001` 功能 / `AC-P-001` 性能 / `AC-E-001` 边界
- 每条 AC 写成「给定 X,当 Y 时,系统 SHALL Z(可观测结果)」
- AI 拿不准的地方写进 §5 并编号 `ASM-001`,**不要静默编造**
- §2.1 的目标只写结果,不写手段("用 Redis 缓存"属于 design)
- **修订已有规范时**(不是第一次写):给变动的 AC 加 delta 标记,
  `<!-- ADDED -->` / `<!-- MODIFIED -->` / `<!-- REMOVED -->`,写在条目行尾。
  这样下游影响面可计算,多 feature 并行时不会互相踩。详见 `conventions.md` 的 delta 章节。

**as-is 模式额外要求**(详见 `references/modes.md`):

- §1.2 写**两层**目标:系统层 + 规范层。只写一层会让全文抽象层漂移
- §2.2 显式写「本期不修改生产代码」
- §3 的 AC 写**现状契约**,必须能被现有测试二值判定;可被环境变量覆盖的常量写
  「默认 X + 覆盖方式」而非字面值
- 采信规则(冲突以实现为准)写进 §2.3
- §6 或等价小节记录「现状与设计意图的偏离」,不写进 §3

### 4. 自检 Gate

对照下面的清单逐条核对。任何一条不通过,回到第 2 步补问,不要带着缺口往下走。

### 5. 展示草稿并确认

把草稿摘要(目标复述 + 做什么 / 不做什么 + AC 数量 + 假设清单)呈现给用户,
用 AskUserQuestion 确认:「按此定稿 / 需要调整 XX / 我要改范围」。

### 6. 固化

1. `python ${CLAUDE_SKILL_DIR}/scripts/init_specs.py <feature>`(若目录尚未创建)
2. 写入 `specs/<feature>/proposal.md`
3. `python ${CLAUDE_SKILL_DIR}/scripts/validate_specs.py --feature <feature>`
4. 更新 §0 版本号为 `v0.1`
5. **AskUserQuestion 确认后** git commit:`docs(spec): 完成 <feature> proposal v0.1`
6. `python ${CLAUDE_SKILL_DIR}/scripts/update_claude_md.py --feature <feature>` 把规范注入 CLAUDE.md

## Gate 检查清单

通用(build 与 as-is 都适用):

- [ ] **目标明确** —— 能写出「本项目要解决 X,让 Y 角色能 Z」,并让用户确认该复述准确
- [ ] **范围有界** —— §2.2 ≥ 3 条,且每条是「本期排除」而非「以后再说」
- [ ] **AC 可测试** —— 每条 AC 能转成一个自动测试用例:明确输入 + 可观测结果 + 二值判定
- [ ] **性能已量化** —— §3.2 每条含具体数字(P95 < 200ms / QPS ≥ 500 / 数据量 ≤ 100 万)
- [ ] **边界已覆盖** —— §3.3 至少覆盖:空输入、超长输入、并发、权限不足、依赖失败
- [ ] **术语一致** —— 术语表存在时正文只用表内词,无同义词混用
- [ ] **可被陌生 AI 理解** —— 不依赖对话上下文,不出现「如上所述」「那个接口」
- [ ] **细粒度适中** —— ≤300 行、≤30 条 AC;超出则提示拆分
- [ ] **模式已判定并告知用户** —— build 还是 as-is,以及覆盖整个项目还是某个 feature

as-is 模式额外:

- [ ] **§1.2 有两层目标** —— 系统层(这个系统要保证什么)+ 规范层(固化成契约)
- [ ] **§2.2 写了不修改生产代码** —— 且用系统行为语言而非交付动作语言
- [ ] **AC 描述现状而非意图** —— 实现与注释不符时,AC 钉实现,偏离记进缺口清单
- [ ] **可覆盖值写了覆盖方式** —— 「默认 0.05,可用 `<ENV>` 覆盖」而非写死 0.05
- [ ] **采信规则已写明** —— 冲突以实现为准,且覆盖规范自身的 ADR 文本
- [ ] **证据已绑定代码版本** —— 实测结论标注了所依据的提交号

## 完成判据

`validate_specs.py` 对该 feature 的 proposal 部分 0 错误,且用户已确认定稿。

**校验怎么跑(两种走法,结果等价)**:

- **脚本走法**:`python ${CLAUDE_SKILL_DIR}/scripts/validate_specs.py --feature <feature>`
- **人工核对走法**(脚本被拒或不可用时):用 Read 读出 `specs/<feature>/proposal.md`,
  对照上面的 Gate 清单逐条核对,把每条的结论(通过 / 不通过 / 不适用 / **未验证**)
  和依据报给用户

脚本走法更稳(不会漏看);人工走法在受限环境里可用。
脚本被拒时按 SKILL.md「受限环境下的降级与解锁路径」的 AskUserQuestion 流程处理。

## 常见坑

| 坑 | 表现 | 修正 |
|---|---|---|
| 把"不做什么"写成"以后再说" | §2.2 变成愿望清单 | 每条都要能判断「本期是否真的没做」 |
| AC 不可测 | 「系统响应要快」 | 换成「P95 < 200ms,并发 500」 |
| 目标里塞了实现 | 「用 Redis 缓存用户信息」 | 目标写结果,手段留给 design |
| AI 默默替用户做决定 | 假设被当成事实写进 §2.1 | 所有假设进 §5 并编号,定稿时一并过目 |
| 术语表写了但正文没用 | 读者按正文理解 | 术语表只收录正文实际出现的词 |
| AC 数量爆炸 | 30 条 AC,细到实现细节 | AC 描述**行为**,实现细节留给 tasks |
| 一句话需求直接开写 | 跳过 Gate | Gate 未过不进 Phase 2 |
| **as-is 的 §1.2 只写规范层目标** | 全文抽象层漂移到「文档」 | 补系统层目标,与 §3 的用户可见 AC 对齐 |
| **as-is 的 AC 写成设计意图** | 规范与代码永久打架,校验永远红 | AC 钉实现,偏离记缺口清单 |
| **AC 里写死可覆盖的常量** | 设了环境变量后 AC 与现实脱节 | 写「默认 X + 覆盖方式」 |
| **把整个项目拆成多个 feature** | 规范层出现多真相源、ADR 编号重启 | 默认项目级一套,模块分区进 design |
