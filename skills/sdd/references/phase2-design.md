# Phase 2 — 架构设计(design.md)

## 目标

把 proposal 的约束转成**可被评审的系统结构**:模块怎么分、职责边界在哪、技术选型是什么、
模块之间怎么对话、非功能约束怎么保证。

design 并非一成不变:阶段 3/4 发现问题可以逆向修改,但必须走文末的流程。

## 输入

- `specs/<feature>/proposal.md`(必读,尤其 §2 范围、§3 全部 AC、§5 假设)
- 现有代码库(如有):模块现状、依赖关系、技术栈

## 输出

`specs/<feature>/design.md`,版本推进到 `v0.5`。

## AI 动作序列

### 0. 划清模块分区

**一个规范集覆盖整个项目时,项目内的各个模块(或子系统)都写进 §1.1 的模块划分表**,
每行一个分区,各自带职责与「不做什么」。

不要把模块拆成多个 feature 目录 —— 拆分的代价是规范层出现多真相源:同一个数字在两份
规范里各钉一次、同一份评测集被重新分类两遍、ADR 编号各自从 001 起导致 `ADR-001`
在两个目录里指两件事。判断依据见 `phase1-proposal.md` 的「覆盖范围」决策。

若项目内确实拆了多个规范集,ADR 编号在**项目内全局连续**,跨文档引用写全限定名
`<feature>/ADR-002`。

### 1. 抽取约束清单

从 proposal 整理出四组:

- **功能边界**(§2.1 / §2.2)
- **全部 AC 编号与要点**——每条 AC 都必须在 design 里有承接
- **非功能指标**(§3.2 的数字、§4 的术语)
- **假设清单**(§5)——design 必须消化每一条假设,或明确标注它仍未解决

### 2. 提议模块划分方案(2–3 套)

每套方案标注:

- 覆盖了哪些 AC
- 违反了哪些约束 / 假设
- 耦合点在哪(哪些模块之间必须通信)
- 复杂度代价(模块数、跨模块调用数、新增基础设施)

不要一上来就给出唯一方案。**至少两套**,让取舍显形——单方案就是把决策藏起来了。

### 3. 枚举技术选型(生成 ADR 草稿)

对每个关键技术决策点:

1. 识别候选:存储、框架、协议、鉴权方式、部署形态、缓存策略、消息队列、日志方案……
2. 每个候选写:优点 / 代价 / 适用条件
3. 写进 ADR(编号 `ADR-001` 递增),格式见 `conventions.md`

ADR **只追加**。放弃旧决策写「已被 ADR-xxx 取代」,原文保留。

**ADR 解释「为什么」,不复述「是什么」。** 行为定义在 proposal §3,是唯一事实源。
ADR 要提到某条行为时,填 `对应 AC: AC-F-012` 引用它 —— 把行为抄一遍就多了一份真相源,
一个行为改动要同步多处。

### 4. 选项化拍板

用 AskUserQuestion 让用户拍板。每个选型问题:

- 选项 = 各候选方案
- 每项写清「优点 / 代价 / 影响哪些 AC」
- 推荐项放首位并标 "(推荐)",并说明推荐理由
- 一次最多 4 个决策点,按影响面排序

同时复核 §2.2 的边界在架构上是否成立:如果某个模块的存在意味着「不做什么」其实做不到,
说明这里有矛盾,要在拍板时一并解决。

### 5. 写 design.md

按模板顺序填写:

1. **系统架构** —— 模块划分 + 职责划分表(做什么 / **不做什么**)+ 数据流向(可选但推荐)
2. **技术选型 ADR**
3. **接口契约** —— 数据模型(只承载语义,不绑实现)+ 模块接口签名(屏蔽内部实现)
4. **非功能性约束** —— 性能 / 安全(key 管理、数据安全、访问控制)/ 错误处理与优雅降级
   (任何失败要有日志记录)/ 可运维性(日志、健康检查、配置热更新)
5. **依赖与假设表** —— 每条假设 + 前提不成立时的退化方案
6. **追溯矩阵** —— 每条 AC → 承接它的设计条目

### 6. 校验与固化

`validate_specs.py --feature <feature>` → 0 错误 → **AskUserQuestion 确认后** git commit:
`docs(spec): 完成 <feature> design v0.5`

## Gate 检查清单

- [ ] 每个模块都有「不做什么」—— 职责边界清晰,耦合点已识别
- [ ] 至少给出过 2 套模块划分方案,且用户知道为什么选了这套
- [ ] 每个 ADR 六要素齐全:标题 / 状态 / 背景 / 选项与优缺点 / 决策 / 理由(关键取舍)
- [ ] ADR 编号递增、无重复、无删除痕迹、取代关系用「已被 ADR-xxx 取代」
- [ ] **ADR 只写「为什么」,没有复述行为**;提到行为的地方用「对应 AC」字段引用
- [ ] 数据模型只承载语义(字段表 + 语义 + 取值约束),不出现建表语句或 ORM 实体
- [ ] 接口签名屏蔽内部实现(伪代码 + 语义 + 错误语义 + 不变量)
- [ ] 非功能约束可验证:性能有数字;安全四问(key 管理 / 数据安全 / 访问控制 / 审计)有答案;
      错误处理保证有日志;可运维性覆盖日志 / 健康检查 / 配置热更新
- [ ] **可配置的数值写明了覆盖方式**(「默认 X,可用 `<ENV>` 覆盖」),与 proposal §3 一致
- [ ] 每条 proposal AC 都能在追溯矩阵里指出承接它的设计条目
- [ ] proposal §5 的每条假设要么已被消化,要么明确标注为未解决风险
- [ ] **项目级规范时,模块分区都落在 §1.1**,没有把模块拆成多个 feature 目录

## 逆向修改规则

阶段 3 或 4 发现设计缺陷时:

1. **停下当前工作**——不要先改代码
2. 说明缺陷:哪个 AC / 哪个接口 / 哪条 ADR 与实现现实冲突
3. 给出 ≥2 个修正方案 + 各自代价
4. AskUserQuestion 让用户选
5. 改 design.md,受影响的 tasks 标记回 pending
6. 在 design.md §7 变更记录留痕(改了什么、为什么、影响哪些 Task)
7. 跑 `validate_specs.py` → 确认 → git commit
8. 回到 tasks 或实现阶段继续

这条规则的存在是为了防止「代码先行、规范事后补」——那样补出来的规范只是对既有代码的
合理化描述,失去了约束力。

## 常见坑

| 坑 | 表现 | 修正 |
|---|---|---|
| 只有一个方案 | 看似省事,实则没让用户做决策 | 至少两套,让代价显形 |
| 模块职责写成了功能列表 | 「负责处理登录」 | 写「负责 X,不负责 Y、Z」 |
| 接口签名绑死实现 | 签名里出现具体类/框架类型 | 只暴露语义与数据结构 |
| ADR 被就地改写 | 历史决策消失 | 追加新 ADR,旧条目标「已被 ADR-xxx 取代」 |
| 非功能约束写「高性能」「要安全」 | 无法验证 | 给数字与可执行手段 |
| 假设消失了 | 需求的隐含前提没人管 | §5 的假设逐条在 design 消化或标风险 |
| 设计推翻需求却不回头改 proposal | 两份文档打架 | 需求变了就改 proposal,再回来改 design |
